# ADR-004 · 解码错误是事件，不是异常（部分结果策略）

- 状态：已接受（2026-09-03）
- 背景：真实采集中坏帧、噪声毛刺、截断是常态；一次坏帧不应毁掉整次解码。

## 决策

解码器**永远返回完整事件列表**；异常片段降级为带 `errors` 标记的事件（`"parity" / "framing" / "break" / "truncated" / "nack" / "spurious-start" / …`），解码在下一个恢复点继续：

- UART → 下一个下降沿（候选起始位）；
- I2C → 下一个 START/STOP 条件；
- SPI → 下一个 CS 边沿 / 采样沿。

截断的采集尾帧输出 `truncated` 事件而非丢弃。渲染层把 `errors` 显示为 WARN/ERR 行（`ann_class`），MCP 层不把它翻译为错误响应。

两圈错误分级：
1. **引擎错误**（抛异常）：缺输入、类型失配（构建期）、参数非法、源文件不可读——包装为 `NodeError(node_id, cause, inputs_summary)`；
2. **数据错误**（事件字段）：信号本身的问题——见上。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 遇错抛异常终止 | 一次毛刺丢失整段数据；与 sigrok/Saleae 实践相悖（它们都以 annotation/warning 呈现坏片段） |
| 错误单独通道（errors 流） | 渲染需 join 两个流才能图文配对；事件自带错误字段更简单 |
| 静默丢弃坏帧 | 用户无法知道丢了什么；不可审计 |

## 后果

- 正面：坏数据下的最大信息保留；测试可注入错误并断言"恢复点后事件完整"；图文配对自然（错误就地标注）。
- 负面：消费方必须检查 `errors` 字段（文档 + 表格状态列强制可见）；`counts()` 同时报告 kind 计数与错误计数，避免静默劣化。
